System objective

What RIS solves

Alert overload

RIS filters incoming events so responders spend time on critical alerts that can impact uptime, customer traffic, or service health.

Slow diagnosis

The LLM enriches alert context and maps incidents to the most relevant runbook, shrinking the time spent searching for recovery steps.

Unsafe automation

Only non-destructive remediation is automated by default, while risky operations are gated behind explicit approval in Slack.

Poor visibility

Execution trails, approvals, and outcomes are mirrored into Slack and backend logs so incident handling stays transparent and auditable.

Architecture

Integrated workflow

1. Alerting tool sends a webhook to the backend codebase.
2. Redis applies rate control before context is handed to the LLM.
3. Runbook search determines whether safe auto-resolution is possible or human approval is needed.
4. Slack captures approvals, status updates, and final audit logs.

Execution model

How RIS handles alerts

Autonomous path

  • Reads incoming critical alert payloads.
  • Enriches context with cluster or service details.
  • Maps to the most relevant runbook.
  • Executes safe remediation using scripts, Ansible, or Kubernetes jobs.
  • Logs the outcome back to Slack and the backend datastore.

Approval-gated path

  • Flags steps with higher blast radius before execution.
  • Pushes a decision request to Slack with alert and runbook context.
  • Waits for human approval or rejection.
  • Performs the chosen action and records the decision trail.
  • Keeps accountability while still accelerating response time.
